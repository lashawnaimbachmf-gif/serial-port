# 验证报告

测试环境：Windows 11 24H2（10.0.26100），COM10（CH340）。1.1.0 时外部 RX/TX 短接已不在位，因此没有重跑硬件 RX 回环；本轮 1.2.0 用合成日志验证 RX 解析/回放，并在 GUI 中验证 GBK 解码与时间戳分段。CLI 的 TX 路径与日志/控制通道继续在 COM10 实机验证。

## 1.2.0 修复与验证

- **文本编码**：终端新增 UTF-8 / GBK 显示编码选择，默认 UTF-8；发送仍按 UTF-8 / HEX，不改变原始字节和日志。GBK 测试日志正确显示“编码：2204369”；切换到 HEX 时编码选择锁定。
- **时间戳分段**：文本渲染增加 1 秒硬间隔；设备行未换行时，超过 1 秒的下一帧仍另起时间戳行。60 秒间隔测试中，`staute =`（21:36:55.283）与 `da217 product code is 0x13`（21:37:55.400）已分离为不同时间戳段。
- **版本**：应用与 CLI 均升级为 **1.2.0**。

## 1.1.0 共享核心改动

GUI 原先通过 Tauri `Channel` 直接发送帧。1.1.0 将“接收/发送/日志/统计”与表现层解耦：

- `serial.rs` 不再引用 Tauri，改为 `FrameSink` 回调；
- GUI 的 `UiSink` 继续编码 `SD01` 二进制帧，帧格式、序号和错误帧行为不变；
- CLI 的 `CaptureSink` 输出 text/JSONL/hex/raw；
- 两种前端共用同一读取线程、写超时、日志写入顺序和结束标记逻辑。

GUI 冒烟结果：连接 COM10 后发送 `GUI-SMOKE-REFACTOR-1`（20 字节），终端出现 TX 帧，TX 计数为 20 B，日志路径正常，断开成功，浏览器控制台无错误。

## CLI 验证细节

- `sdesk ports --json` 返回 `COM10 / USB-SERIAL CH340`；只有一个串口时 `capture` 可省略 `--port`。
- 后台 `sdesk capture --port COM10 --json`：首行 `session` 包含端口、波特率、日志路径、控制端口；`sdesk sessions` 显示 `running`。
- `sdesk send --port COM10 --data "PING\r\n"`：通过控制通道发送，返回 `{"ok":true,"bytes":6,...}`，无需重新打开串口。
- 日志内容与 GUI 格式一致：`2026-10-19 13:33:51.284 | TX      6 B | PING\r\n`。
- `sdesk stop --port COM10`：进程正常退出，日志追加 `# closed: ... | RX 0 B / 0 frames | TX 27 B / 3 frames`，状态文件被删除。
- `sdesk capture --no-control --quiet --no-log --timeout 1`：自动选择唯一串口、无日志、退出码 0。
- `--until` 无匹配时退出码 3；`--log-interval 1`、`--baud 1` 退出码 2 且给出明确原因。
- `sdesk log list` 正确显示端口、开始时间、大小、帧数与 `closed` 状态。
- `sdesk log tail --follow --lines 0`：向文件追加两帧后，两帧依次以 JSONL 输出，超时退出码 0。
- 合成日志覆盖：中文（6 字节）、`\x00\x01\x7F\x80\xFF`（5 字节）、非法 UTF-8（`\xFF`）、`--grep`、`--since`、`--direction`、`--limit/--offset`。

## 1.0.0 硬件回环记录（历史）

当时 COM10 的 RX/TX 已外部短接：

- 波特率下拉共 20 档；选中 9600 后实际以 **9600 bps / 8-N-1** 打开 COM10，并成功回环 `BAUD-9600-OK`。
- 日志面板收起后终端宽度为 **1160 px**（原为 890 px）；隐藏期间发送 `LOGGING-WHILE-HIDDEN`，RX/TX 均增至 **57 字节 / 4 帧**，日志从 **659 B** 增至 **791 B**；展开后恢复。
- 115200 下文本消息 `DSH-闭环-20261019-B8E4` + CRLF 共 **26 字节**；二进制 `00 01 7F 80 FF` 共 **5 字节**；发送与接收 HEX 完全一致，共 **31 字节 / 2 帧**。
- 日志同时包含 TX/RX、中文、`\r\n` 转义和 `\x00\x01\x7F\x80\xFF`；5 秒定时保存向前推进；断开后新增 `# closed`，显示 `RX 31 B / 2 frames | TX 31 B / 2 frames`。
- 关闭窗口测试：保存间隔设为 3600 秒，连接 COM10、发送、收到回环后直接关闭窗口；日志包含 TX、RX 与 `# closed`，证明关闭窗口走会话收尾逻辑而不是丢弃文件句柄。

### 本轮发现并修复

- `sdesk stop --json` 在没有任何运行中会话时曾输出中文提示而不是 JSON。现固定输出 `[]`，并新增 CLI 端到端测试 `stop_json_without_sessions_is_an_empty_array`。
- 串口打开失败的底层错误已带中文句号，上层再补句号会形成“拒绝访问。。”。现统一去掉重复标点。
- 日志面板开关原写作“收起日志/展开日志”，容易被理解为停止日志记录，而且按钮放在终端工具栏里。现改为面板标题“保存日志”，收起按钮放进面板头部，收起后显示独立的“展开日志”按钮；悬停提示明确“不影响日志记录”。实机验证：终端宽度 890 → 1160 px，工具栏与面板头部均无横向溢出。
- 时间戳原来插在数据流中，设备一行尚未结束时会被打断。现改为左侧固定时间栏（文本模式 104 px），只在行首显示；未换行的后续帧继续接在同一行，TX/RX 中途切换先换行。仅 `TerminalView`/CSS 改动，串口读取、帧序号和日志不受影响。实机验证：所有数据行从同一列开始，CRLF 被拆到两帧时也不会产生空时间戳行。截图见 `artifacts/ui-timestamp-gutter.png`。

## GUI 启动修复（1.1.0）

问题：双击图标后窗口约 2–3 秒才出现。

定位：窗口配置为 `visible: false`（避免白屏），原本只在 `on_page_load` 事件里调用
`show()`。实测该事件在 Windows 上没有可靠触发，窗口一直隐藏，最终由 `setup` 中的 3 秒
兜底线程显示。用 Win32 `EnumWindows` 跟踪主窗口：

- 修复前：442 ms 时主窗口已创建但不可见，**3712 ms** 才变为可见。
- 修复后：前端在 `initialize()` 开始时调用新增的 `show_main_window` 命令，
  `Start-Process` 路径 **611–772 ms** 可见，Explorer 双击路径 **1083–1227 ms** 可见，
  且启动后即为前台窗口。
- 3 秒兜底保留，仅用于前端初始化失败的情况。

剩余约 0.6 秒主要是 Tauri/WebView2 创建窗口本身的耗时。验证环境：Windows 11 24H2、
64 GB 内存、NVMe SSD、Defender 实时保护关闭，启动前无其他 SerialDesk 实例。

## GUI 日志回放与文本显示（1.2.0）

- “保存日志”面板新增“打开日志”：仅在未连接串口时可用；原生文件选择器只筛选 `.log`。
- Rust 后端直接复用 CLI 的日志解析器（通过源码包含，不是第二套格式实现），严格校验时间戳、方向、字节数与转义；无效行计数并提示，不会伪造数据。
- 前端回放复用现有终端，保存/恢复打开回放前的终端快照与计数；回放期间禁止连接串口和清空终端，状态栏显示“日志回放 / 只读”。
- 支持文本/HEX、UTF-8/GBK 显示编码、时间戳开关、自动跟随、收起日志面板；回放结束按钮或 `Esc` 返回实时界面。
- 时间戳：文本模式下，超过 1 秒的帧间隔即使设备还没换行，也另起时间戳行；普通同一条设备行碎片仍会合并。
- 单次回放最多载入 50,000 帧且载荷不超过 8 MiB；超出时只显示最近部分并在回放栏明确提示，日志文件本身不被修改。
- 实机：`read_log_file` 返回 3 帧、RX 50 B / 3 帧；GBK 测试日志正确显示“编码：2204369”；`staute =`（21:36:55.283）与 `da217 product code is 0x13`（21:37:55.400）被分到不同时间戳段；HEX 与日志内容逐字节一致；原生对话框打开和退出均通过。
